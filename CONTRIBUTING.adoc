= Contributing to AI Agent Skills

Thank you for your interest in contributing to AI Agent Skills! This document provides guidelines and instructions for contributing to this project.

== Ways to Contribute

You can contribute to this project in several ways:

- Creating new skills for programming languages, frameworks, or tools
- Improving existing skills with better examples or explanations
- Fixing errors or inconsistencies in the documentation
- Adding translations for skills
- Improving the project structure or tooling
- Reporting issues or suggesting improvements

== Getting Started

=== Prerequisites

Before contributing, ensure you have:

- A GitHub account
- Git installed on your local machine
- Basic understanding of Markdown and YAML frontmatter
- Knowledge of the technology you are creating a skill for

=== Setting Up Your Development Environment

. Fork the repository on GitHub
. Clone your fork locally:
+
[source,bash]
----
git clone https://github.com/zademy/ai-agent-skills.git
cd ai-agent-skills
----

. Create a new branch for your changes:
+
[source,bash]
----
git checkout -b feature/your-skill-name
----

. Make your changes
. Test your changes locally
. Commit your changes:
+
[source,bash]
----
git add .
git commit -m "Add: Description of your changes"
----

. Push to your fork:
+
[source,bash]
----
git push origin feature/your-skill-name
----

. Create a Pull Request on GitHub

== Creating a New Skill

Skills are organized in directories with the following structure:

----
skill-name/
└── SKILL.md
----

=== Skill File Structure

Each skill must include YAML frontmatter at the top:

[source,yaml]
----
---
name: skill-name
description: A brief description of what this skill does and when to use it
---
----

=== Naming Conventions

- Skill names must be lowercase
- Use hyphens instead of spaces (e.g., `virtual-threads` not `virtual threads`)
- The `name` field must match the parent directory name exactly
- Descriptions should be concise (max 1024 characters)

=== Skill Content Guidelines

Follow these guidelines when creating or modifying a skill:

. Write clear, actionable instructions
. Include practical code examples
. Use consistent formatting throughout
. Explain concepts before showing code
. Keep examples focused and relevant
. Test all code examples before submitting

=== Example Skill Structure

[source,markdown]
----
---
name: example-skill
description: This skill explains how to do something useful
---

# Skill Title

## Overview

Brief introduction to the concept.

## Basic Usage

Example code demonstrating the skill.

[source,language]
----
// Your code here
----

## Advanced Topics

Additional information for advanced users.

## Common Patterns

Frequently used patterns or best practices.
----

== Style Guide

=== Writing Style

- Use clear, concise language
- Write in American English
- Use active voice
- Avoid jargon when simpler alternatives exist
- Explain technical terms on first use

=== Code Examples

- Use syntax highlighting for code blocks
- Include comments for complex logic
- Show both simple and advanced examples
- Test all code before submission
- Use consistent indentation (2 spaces for most languages)

=== File Naming

- Use lowercase for all file names
- Use hyphens to separate words
- End file names with `.md` for Markdown files
- End file names with `.adoc` for AsciiDoc files

== Pull Request Process

When submitting a Pull Request:

. Fill in the required template
. Include a clear description of your changes
. Reference any related issues
. Ensure all tests pass
. Request review from maintainers

=== PR Title Guidelines

- Use clear, descriptive titles
- Prefix with the type of change:
  - `Add:` for new skills
  - `Update:` for improvements
  - `Fix:` for bug fixes
  - `Refactor:` for code restructuring

=== PR Description Template

[source,markdown]
----
## Description
Brief description of the changes

## Type of Change
- [ ] New skill
- [ ] Update existing skill
- [ ] Bug fix
- [ ] Documentation update

## Checklist
- [ ] Skill name matches directory name
- [ ] YAML frontmatter is valid
- [ ] Code examples are tested
- [ ] Documentation is clear
- [ ] No empty directories

## Related Issues
Closes # (if applicable)
----

== Code Review Process

All submissions require review before merging. Reviewers will check:

- Compliance with naming conventions
- Validity of YAML frontmatter
- Quality of code examples
- Clarity of documentation
- Overall consistency with existing skills

== Adding Multiple Technologies

When adding skills for multiple related technologies:

. Create separate directories for each technology
. Use clear, descriptive names
. Reference related skills where applicable
. Maintain consistency in structure across related skills

== Quality Standards

To maintain quality, all skills should:

- Be accurate and up-to-date
- Follow the project's naming conventions
- Include practical, working examples
- Be written in clear English
- Follow accessibility best practices
